lmr

Technical Manual

An offline research assistant, and the experiment that decided how to build it. It answers questions from 297 Wikipedia articles using only what runs on this machine: a keyword index, one 17-million-parameter reranker and a 1.5-billion-parameter language model. The research behind it asked whether better retrieval matters on a device. The answer was no, but better packing does.

Part I

Orientation

What the tool does, how to run it, and what it knows.

1

What it is for

A lookup tool for when there is no network, and a measured answer to which parts of one are worth building.

1.1 The tool

Ask a question in a terminal (lmr ask) or a local web page (lmr serve). The assistant searches its corpus, picks the paragraphs that fit a fixed budget, and has a local model write an answer that cites them. Nothing leaves the machine: the language model is a llama-server bound to 127.0.0.1, and the reranker runs on the CPU in-process.

The web page shows every stage of an answer, not just the result: which paragraphs keyword search found, how the reranker reordered them, which ones fit the 1,000-token budget, and which the model cited (Fig. 2.2).

1.2 Where it came from

The project started as a response to a public bounty: “Build the Best Offline AI Research App for Android” (poidh #31, about 1.5 ETH, closing 2026-10-31). Its bar is a phone app under 12 GB of RAM that is “more than 50% as good as internet plus frontier models”, with no network at all.

Instead of building an app first, this project asked a narrower question that any such app has to answer: on a phone-sized model, does retrieval quality actually change the answer, and what is the cheapest design that captures the difference? The generator was held fixed on purpose, so that if evidence quality barely moved the answer, the project could say so.

Scope

Every measurement in this book was taken on a desktop CPU. None of it is a claim about Android or GrapheneOS performance. The Android app is not built (Chapter 10).

2

Running it

Three commands from a fresh clone. The first one downloads 1.2 GB and rebuilds the corpus; after that nothing touches the network.

# Python 3.11+, uv. CPU only. git clone https://github.com/davidghatley/local-mobile-research && cd local-mobile-research uv venv && uv pip install -e ".[rerank]" .venv/bin/lmr setup # llama.cpp b11227 (CPU) + Qwen2.5-1.5B GGUF, sha-checked; corpus from 297 pinned revisions .venv/bin/lmr ask "Which planet is closest to the Sun, and how long is its year?" .venv/bin/lmr serve # http://127.0.0.1:8765

3

The corpus

297 articles chosen before any question was written, weighted towards names that mean several things at once.

Fig. 3.1 · Articles per topic clusterCounted from corpus/corpus.jsonl
Why “confusable”
  1. Same nameMercury the planet, element, god, car, label and singer
  2. Same wordskeyword search scores them alike
  3. Same groupkept in one split, so no answer leaks across

Fig. 3.1 — More than a third of the corpus is deliberately ambiguous, which is where a reranker should earn its keep.

3.1 Pinned, then rebuilt

corpus/provenance.json records, for each article, the Wikipedia revision id and the sha256 of its wikitext. lmr setup fetches those exact revisions (not today’s pages), refuses any whose bytes differ, and runs the original offline converter. All 297 matched on 2026-10-15.

Verify

The rebuild reproduces the research numbers exactly: BM25 packet completion is 54/73 on dev and 80/122 on shadow_dev, the same as the frozen round-1 results, and all 235 gold evidence ids resolve. One known difference: article-level cross-links came from a live API list at the original fetch and are re-derived from wikitext here, so the file hash differs. Retrieval does not read them.

Part II

The finding

Retrieval was already good. The evidence got lost on the way to the model.

4

Found is not shown

BM25 found almost every paragraph a question needed. A quarter of them never reached the model.

Fig. 4.1 · Where required evidence goes · dev, BM2573 required paragraphs · loss_attribution_B1_bm25_dev_core.json
Key
  1. Searchheadroom here is 4.1%
  2. Per-article capthree paragraphs per article, max
  3. Token budget1,000 tokens ≈ 3 paragraphs

Fig. 4.1 — The problem is allocation, not recall. A paragraph averages about 280 tokens, so the budget holds roughly three; which three is the whole game.

Lifting the per-article cap only moved completion from 54 to 56 of 73: the loss migrated from the cap to the budget. The two limits are substitutes. What helps is putting the right three paragraphs first.

5

The reranker is an allocator

A 17M cross-encoder found nothing new. It reordered what BM25 already had, and 13 points more of the needed evidence reached the model.

Fig. 5.1 · Packet completion, BM25 vs the 17M rerankerFrozen round-1 runs · Wilson 95% intervals
Key
  1. BM25keyword search, no model
  2. Rerankerettin-17m on BM25's top 500
  3. Pooled+26 paragraphs vs an 18-item threshold

Fig. 5.1 — The only result in round 1 to clear its preregistered threshold. On dev alone (+10 vs a 13-item threshold) it would have been recorded as a null.

Every reranking stage read exactly the same search survival as BM25 (70/73): a reranker cannot add a paragraph BM25 did not return. The gain came entirely from the order, and it arrived using fewer tokens (740 vs 798 per packet on shadow_dev).

5.1 How deep does the reranker need to look?

The research reranked all 500 candidates, which cost 40 s per question on one thread. The app reranks only the top k. Measured with lmr bench on this machine:

Fig. 5.2 · Completion and latency against rerank depthMeasured · lmr bench · desktop CPU
  • dev · 73 required
  • shadow_dev · 122 required

Fig. 5.2 — Most of the gain arrives by k = 20; k = 100 matches the full 500 within one paragraph per split at about a quarter of the time. Retrieval only (BM25 + rerank); generation adds about 4 s. Source: docs/manual/data/bench_*.json.

Decision

The app defaults to --rerank-k 100. Pooled over both splits it keeps the full-depth result (160/195 required paragraphs) at about a quarter of the latency; k = 50 gives 157/195 in two-thirds of that time. The app and the frozen research system agree exactly at k = 500 on both splits (64/73, 96/122), which is a second check that the rebuilt corpus is faithful.

Bigger was not better. The 68M reranker beat the 17M by one paragraph at four times the size.

7

The generator ceiling

The 1.5B model can tell good evidence from bad, but even perfect evidence only gets it to about one answer in seven.

Fig. 7.1 · Exact-match accuracy by evidence givenGENERATOR_FLOOR_REPORT.md · 137 analysable questions
Reading it
  1. It listensgold beats wrong evidence on all 19 discordant items, p = 3.8×10⁻⁶
  2. It caps outperfect retrieval buys 4 answers; detecting a difference needs 18

Fig. 7.1 — No retrieval change can show up in final answers on this corpus with this model. That is a property of the generator, found before any architecture was compared.

Pitfall · citations

The fixed prompt asks for bracketed citations. In practice the 1.5B model rarely emits them (none in six sample questions on 2026-10-15) and adds facts that are not in its evidence. Asked how Freddie Mercury got his stage name, it answered that the stage name was “Farrokh Bulsara”, which is his birth name. Asked to compare Mercury the planet and the element, it claimed both have atomic number 80. The UI shows which packet paragraphs were cited, so this is visible rather than hidden.

This is the clearest next step: fine-tune a small model to write short, cited answers from a packet (Chapter 10).

Part III

Method

How the results above were protected from wishful thinking.

8

How the experiment was run

Thresholds first, systems second, the confirmation split once.

Fig. 8.1 · Smallest difference each split can detectexperiments/comparability/CONTRACT.md §4

Fig. 8.1 — A gap shorter than its bar is recorded as a null result, never a win. The reranker clears only the pooled bar it was tested against.

  • Preregistration. Hypotheses, thresholds and kill conditions were committed before code (experiments/*/HYPOTHESIS.md), and the BM25 parameters are pinned to the bit (experiments/common/bm25.py).
  • One shot at confirmation. The reranker's configuration was frozen (FREEZE_RECORD.md) before its single shadow_dev run.
  • Sealed test. 116 private questions were written, reviewed and sealed outside the repository; only their counts and hash are tracked. No system was ever scored against them.
  • A freeze gate. scripts/verify_round0 checks ten stages (hashes, splits, leakage, custody) and docs/probes_round0.sh runs eleven adversarial probes against it.
9

What the reviews caught

Eight independent freeze reviews. Seven said “repair required”. Each defect was invisible to the checks written by the same team.

DefectWhy the existing check passed
A partition census that agreed with itselfIt was derived from the data it was meant to check
A truncated partitionIt passed three consecutive stages because each stage was internally consistent
A fix defeated by editing the data and its census togetherBoth sides moved; the trust root had to move outside the repo
A stage that compared nothing and printed PASSVacuous success: no test asserted the stage had inputs
A leakage gate that could never pass, then one that leakedOnce repaired it worked as a membership oracle and had to be re-scoped
A preregistration anchor pointing at a commit without the policy fileNobody resolved the anchor
A minimum-difference figure wrong by about 2×Refuted by its own worked example three lines earlier
Lesson

An internal consistency check is necessary and never sufficient. The same failure shape appeared for a single item, a whole partition and the entire freeze. Every one of them was found by a fresh reader. The full account is in docs/ROUND0_CLOSURE.md.
